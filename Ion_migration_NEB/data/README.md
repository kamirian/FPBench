# Standardized data files

> **Archived deposit.** `ion_migration_neb_reference.json.gz` is also archived under a
> citable DOI at <https://doi.org/10.6084/m9.figshare.33332610>, together with this
> README. The deposited copy is byte-identical to the one in this repository; verify
> with the SHA-256 in the table below. The analysis and generation code that consumes it lives at
> <https://github.com/mogroupumd/FPBench>. The other two files described below, the
> leaderboard summary and the all-FP results file, are not part of the deposit.

## `ion_migration_neb_reference.json.gz`

The canonical DFT-NEB reference (154 active pathways across 109 unique
structures, 7 finalized DFT-NEB images per pathway, 1,078 images total).
Shipped directly in this repository -- small enough that no external hosting
or Git LFS is needed.

| Filename | Uncompressed size | Uncompressed SHA-256 | Compressed size | Compressed SHA-256 |
|---|---|---|---|---|
| `ion_migration_neb_reference.json.gz` | 68.1 MiB | `f673135dd05b42371f23de1f89e3cd14729605c5ddd2f3672376785d8c88b4bf` | 9.9 MiB | `e211dc4a88fe5739218d6b1e47404624225c5a0d787f4dcce3ef61a5574087c4` |

Produced by a deterministic gzip (fixed compression level, no embedded
timestamp or filename) of the private project's approved
`input_data/ion_migration_neb_reference.json`; decompression was verified to
reproduce the exact same JSON content (byte-for-byte) before this file was
committed.

Both the analysis and generation notebooks' loaders accept `.json` and
`.json.gz` (detected by file extension).

## `ion_migration_neb_leaderboard_summary.json`

A compact, deterministic per-FP summary (schema version, active-pathway
count, source-file checksums, units, metric-column descriptions, one record
per FP with separate MAE/RMSE numeric fields, `n_nonconverged`/`n_total` as
integers) used directly by the leaderboard website -- no structures, image
force arrays, or other large records. Generated by the public
`scripts/export_neb_leaderboard.py` (run from the `Ion_migration_NEB/`
directory) from the same unmodified `neb_analysis.py` functions the analysis
notebook itself calls, cross-checked against
`compute_key_neb_metrics_summary`'s own formatted values before being
written, so it cannot silently drift from what `analysis/neb_analysis.ipynb`
displays. That script writes this file and an identical copy at
`../docs/data/ion_migration_neb_leaderboard_summary.json` (the copy the
GitHub Pages leaderboard actually fetches). See that script's docstring for
the exact generation command.

## `ion_migration_neb_results_standardized.json` (not committed here)

The full standardized all-FP results file (`full_fp_neb`,
`fp_static_on_dft_neb`, and `dft_static_on_fp_neb` for all seven FPs) is
**not** committed to this repository -- at ~323 MB it is well beyond what is
practical to version-control directly, the same reasoning as the Force
Prediction component's standardized files.

| Filename | Approx. size | SHA-256 |
|---|---|---|
| `ion_migration_neb_results_standardized.json` | ~323 MB | `62a2447a4d121598772a6e14a7fd5814668b397d4faee8433dcd1ad035519799` |

**This file is deliberately not archived.** Every FP result in it is
re-derivable by running the seven FPs on the reference structures shipped
here, which is what this benchmark exists to make possible, so depositing a
323 MB derived artifact would add storage cost without adding
reproducibility. The reference structures and the generation code are the
archived, citable parts. To work with results, use one of:

- The small real example under `../examples/` (`ion_migration_neb_demo_data.json`),
  which requires no download and exercises the same public functions.
- `../generation/fp_neb_generation_and_run.ipynb` and
  `../generation/dft_static_on_fp_neb.ipynb` to regenerate your own results
  file against the shipped reference, on your own cluster and FP
  environments.

### Where to place it

Regenerate as described below, then place the file at
`ion_migration_neb_results_standardized.json` in this `data/` directory. The
analysis notebook loads it as `../data/ion_migration_neb_results_standardized.json`.

### Regenerating from scratch

1. `../generation/fp_neb_generation_and_run.ipynb` generates `full_fp_neb`
   and `fp_static_on_dft_neb` jobs against the shipped reference, and merges
   completed results into a candidate file under its own `runs/.../merged/`
   directory (never overwriting anything in this `data/` directory).
2. `../generation/dft_static_on_fp_neb.ipynb` reads that (or the canonical)
   results file, generates VASP static calculations on the final full
   FP-NEB images, and merges parsed results into the `dft_static_on_fp_neb`
   branch of a new candidate file.
3. Promotion of a validated candidate to
   `ion_migration_neb_results_standardized.json` is a manual step -- neither
   notebook performs it automatically.

This requires a working environment per FP family and, for the full
154-pathway population, an HPC cluster. See each generator notebook's
Configuration section, and the component
[README](../README.md#reproducing-the-benchmark).

## Schema

**`ion_migration_neb_reference.json.gz`**, after decompression:

```python
reference_data = {
    "schema_version": "...",
    "component": "ion_migration_neb",
    "units": {"energy": "eV", "forces": "eV/angstrom"},
    "common_pathway_keys": [...],   # the 154 active pathway keys
    "excluded_pathways": {...},     # informational only; not part of the active 154
    "pathways": {
        "<icsd_id>|<source_path_id>": {
            "identifiers": {"pathway_key": "...", "icsd_id": "...", "source_path_id": "...", "sum_formula": "..."},
            "full_fp_neb_input": {
                "source_start_endpoint_structure": {...},   # unrelaxed
                "source_end_endpoint_structure": {...},     # unrelaxed
            },
            "endpoint_correspondence": {"orientation_relation": "direct | unresolved", ...},
            "dft_neb_reference": {
                "images": [
                    {
                        "image_index": 0,
                        "endpoint_role": "initial | intermediate | final",
                        "structure": {...},
                        "energy_total_eV": ...,
                        "forces_eV_per_angstrom": [...],
                    },
                ],
            },
        },
    },
}
```

`full_fp_neb_input` (unrelaxed source endpoints) and `dft_neb_reference.images`
(finalized DFT-NEB images) are two separate inputs, used by two separate
protocols, never substituted for each other. `endpoint_correspondence` is
traceability metadata only, never read by the full FP-NEB workflow: 152
pathways have `"direct"` orientation, 2 have `"unresolved"` (the structural
evidence does not clearly support "direct" for those two), 0 are
"reversed" -- none of this affects whether a pathway's `full_fp_neb_input`
or `dft_neb_reference` is complete or runnable.

**`ion_migration_neb_results_standardized.json`** (schema documented for
when it becomes available; not shipped here):

```python
fp_results = {
    "schema_version": "...",
    "component": "ion_migration_neb",
    "units": {"energy": "eV", "forces": "eV/angstrom"},
    "models": {
        "<fp_key>": {
            "full_fp_neb": {
                "pathways": {"<pathway_key>": {"identifiers": {...}, "neb_status": {...}, "final_fp_neb_images": {...}}},
                "unsuccessful_pathways": {...},
            },
            "fp_static_on_dft_neb": {
                "pathways": {"<pathway_key>": {"identifiers": {...}, "images": {...}}},
                "unsuccessful_pathways": {...},
            },
            "dft_static_on_fp_neb": {
                "pathways": {"<pathway_key>": {"identifiers": {...}, "images": {...}}},
                "unsuccessful_image_attempts": {...},
            },
        },
    },
}
```

Three protocol branches, never mixed: `full_fp_neb` (the FP's own relaxed
endpoints and climbing-image NEB path), `fp_static_on_dft_neb` (the FP
evaluated, single-point, on the DFT-NEB reference's own images), and
`dft_static_on_fp_neb` (DFT evaluated, single-point, on the FP's own final
`full_fp_neb` images -- intentionally sparse coverage, never padded).

## Unsuccessful and non-converged records

- `calculation_status`: `not_run`, `missing`, `interrupted`, `failed`,
  `partial`, or `completed`. Always separate from scientific convergence.
- A completed full FP-NEB run can have `neb_status.neb_converged: false`
  (completed, but did not satisfy the NEB force-convergence criterion) --
  preserved and reported, never dropped or treated as failed.
- Failed/missing/interrupted/not-run `full_fp_neb` and `fp_static_on_dft_neb`
  records live in a sibling `unsuccessful_pathways` branch; rejected/failed/
  missing/not-run `dft_static_on_fp_neb` image attempts live in
  `unsuccessful_image_attempts`. Both are read by the analysis functions for
  status/coverage reporting only -- never for any scientific metric, and
  never changing an existing metric's denominator.

## Loading

```python
import sys
sys.path.insert(0, "../scripts")
from neb_analysis import load_neb_datasets, build_neb_analysis_results

reference_data, fp_results = load_neb_datasets(
    "ion_migration_neb_reference.json.gz",
    "ion_migration_neb_results_standardized.json",   # after downloading/regenerating
)
results = build_neb_analysis_results(reference_data, fp_results, expected_pathways=154)
```
